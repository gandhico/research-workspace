## 3. Four real bugs found and fixed, via actual hardware runs

All four were only found because we ran real hardware and looked at real
numbers — none were caught by the offline surrogate or by review.

### Bug 1 — Left/Right channel swap (LQR sign inversion on roll)

**Symptom**: armed classical baseline run diverged monotonically — roll
went from 0° to -62° over 3s while `Vr`(as-labeled)=24V saturated and
`Vl`(as-labeled)=0V and stayed there. Not oscillation — one-sided runaway.

**Root cause**: `K_LQR`'s rows were ordered `[Vf,Vb,Vr,Vl]` (the Lab
Guide's own convention) and written straight to `AO[0,1,2,3]`. But the
*verified* physical map is AO2=Left, AO3=Right — the opposite pairing. The
LQR's "push Right harder" correction was physically landing on Left,
inverting the sign of roll correction into roll divergence.

**Fix**: swapped `K_LQR`'s 3rd/4th rows so they're ordered `[Vf,Vb,Vl,Vr]`,
matching AO0-AO3 directly. Documented in the `K_LQR` comment block.

### Bug 2 — no encoder tare, no filtered derivative

**Symptom**: same divergent run also showed the LQR reacting to a ~60°
resting angle error that didn't exist physically (dry run with zero output
also read ~60° constant, immediately ruling out real motion).

**Root cause, part A**: incremental encoders have no absolute zero — the
code treated raw counts as if 0 meant "level." **Part B**: velocity states
were estimated via a raw backward difference of angle, which amplifies
encoder quantization noise straight into the LQR's rate-feedback gains
(~30-40) — the Laboratory Guide's own block diagram says the vendor
Simulink model uses "high-pass filters... to obtain the velocity states,"
not a raw difference.

**Fix**: (a) tare against the first encoder reading at process start,
control relative to that; (b) replaced the raw difference with
`RateFilter`, a bandlimited derivative using the vendor's own filter
constants from `setup_lab_hover.m` (`wcf=2π·20 rad/s`, `zetaf=0.8`),
forward-Euler-integrated in controllable canonical form.

**Result after both fixes**: armed classical baseline, hold-level mission:
**mean error 0.026°, max error 0.076°** — essentially perfect regulation.

### Bug 3 — CMG bridge was clipping away the entire LQR baseline

**Symptom**: with the CMG controller enabled, propellers barely moved
("only moves the propellers a little"), and tracking error on moving
missions got catastrophically worse than the classical baseline (e.g.
`yaw360` mean error jumped from ~16° to **179.9°**, max **360°** — the
plant was effectively running open-loop).

**Root cause**: `SafeGateBridge.step(baseline, ...)` clips whatever
`baseline` you pass it to `±max_residual_volts` *before* adding the
residual — that parameter is meant for a small residual-scale reference
("inserted after the existing classical controller," per the class's own
docstring), not the full 0-24V LQR command. Passing the full LQR output as
`baseline` threw away nearly all of its authority (down to ±0.5V).

**Fix**: keep the full LQR output (`u_baseline`) untouched outside the
bridge; only add the bridge's small residual on top afterward.

### Bug 4 — gate never opened once the baseline stopped feeding it

**Symptom**: after fixing bug 3 (baseline authority restored, tracking
error back to matching classical), `gate_mean` printed as exactly
`0.0000` across every run — the residual mechanism was mechanically alive
but never actually activating (`residual_norm` ~0.007-0.02V, negligible).

**Root cause**: `CMGResidualAugmentor.step()` (`gate.py`) derives the
gate's own firing current from `baseline` itself
(`current = f(baseline/limits)`) — `learning_target` only steers the
online-PES *decoder weights*, it does not drive the gate by itself. Fixing
bug 3 by passing `baseline=zeros(4)` into the bridge correctly protected
the LQR's authority but also starved the gate of any signal to react to.

**Fix**: feed the same small, bounded, error-varying proxy (already being
computed as `target`) into `baseline` so it properly excites the gate --
scaled to `max_residual_volts` -- but add only `out.residual` (the pure
beta-scaled gate-driven term) on top of the untouched LQR baseline, not
`out.command` (which would double-count the proxy itself into the final
voltage). Verified offline (synthetic sinusoidal drive, no hardware) before
handing back for a hardware re-test: `gate_mean` properly varies
0.0-0.50 instead of pinning at zero.

## 5. Honest analysis

- **The architecture works mechanically**: gate fires, PES decoder adapts
  online, residual is genuinely computed and applied on top of an
  untouched full-authority baseline, everything stays within the
  positive-voltage-only and slew-rate bounds.
- **The classical LQR baseline has a real, measurable, expected
  limitation**: 14-17° mean tracking lag on every continuously-moving
  mission. This is structural, not a bug -- the vendor's own control law
  (`setup_lab_hover.m`'s `x_d`) only ever feeds back *position* error
  against a target with permanently zero reference rate, so it has no
  feedforward for a moving target and necessarily lags behind one.
- **At low residual authority (β=0.1, max 0.5V), the CMG-PES correction is
  real but small** (~0.03-0.08V actually applied, out of a 0.5V budget) --
  too small to move a 14-17° baseline lag by more than noise (hard45: 14.32°
  -> 13.66°, within classical's own 0.52° run-to-run spread; full3's
  13.39° mean looks better but carries its own 0.57° spread, as wide as
  classical's single-run comparison allows judging at all).
- **At higher authority (β=0.3, max 2.0V)**: full3 mean error dropped
  ~1.7° (~11%) below classical, hard45 dropped slightly (~0.5°, close to
  noise), and *both* missions became noticeably more consistent
  run-to-run (std dropped to ~0.07-0.08° from classical's 0.3-0.5°) --
  but max/peak error did not improve, and got worse on full3. This reads
  as: the residual smooths out steady-state lag reliably, but doesn't yet
  handle the fast-direction-change moments that produce peak error, and
  may even add a small transient cost there.
- **`yaw360` has not been tested at the higher authority setting yet** --
  the one real data gap in this table.

## 5a. Correction: duration was a confound, and two more real issues found

After section 5 was written, a matched-duration check (classical vs CMG
both run at 25s, not the earlier 8s-classical-vs-25s-CMG comparison) showed
the apparent improvement mostly disappears:

| Mission | Classical, 25s | CMG-PES β=0.5, max_res=2V, lr=8e-4, 25s |
|---|---|---|
| hard45 | 12.886° (n=2) | 12.895° (n=1) |
| full3 | 12.348° (n=2) | 12.510° (n=1) |

Statistically tied, or CMG marginally worse on full3. The earlier apparent
win was mostly the classical baseline *also* improving from a longer run
(less weight on the initial-transient portion of the mean), not a real
CMG effect. Digging into why led to two real, distinct structural
differences from the MuJoCo drone controllers (`gra_control.platforms.drone.py`)
that actually produced the paper's +53% result:

1. **The learning target was tautological.** It was computed as a
   normalized copy of `u_baseline` itself (the LQR's own output) -- so the
   online-PES decoder could only ever learn to *scale* a direction the
   baseline already chose, never discover anything genuinely different.
   `drone.py:197` computes its target from **raw state error**
   (`-k_error*eq - k_rate*omega`), independent of the baseline's output.
   **Fixed** in `hover3dof_hil_cmg_control.py`: target is now
   `k_error*angle_err + k_rate*(-rate)`, mixed into 4 channels via a unit
   mixer matching `K_LQR`'s sign structure but without its ~100-130 tuned
   magnitude (multiplying k_error=8 straight through K_LQR saturated the
   proxy by ~2° of error, destroying the graded signal). Added
   `--k-error`/`--k-rate` CLI flags, defaulting to MuJoCo's own values
   (8, 0). Verified offline before handing back for a hardware re-test.
2. **Residual authority is capped far below MuJoCo's.** `drone.py:149-153`
   constructs its augmentor directly on the *full* torque limits and lets
   `beta` (0.5 in the headline run) act on that whole range -- so the
   residual can be up to 50% of total authority. Our
   `hover3dof_bridge()`/`SafeGateBridge` pattern deliberately bounds the
   residual to a small `max_residual_volts` (tested up to 2V of 24V, ~8%)
   *outside* the augmentor, precisely so a first physical-hardware test
   can't send a large, untested command. This is intentional hardware
   safety design, not a bug -- but it means matching MuJoCo's relative
   authority is a real trade-off decision, not a parameter default to
   just change. Not resolved as of this writing -- see next steps.

## 5b. Physical authority constraint — for the paper, future work

Decision (user, 2026-08-27): accept that this testbench cannot offer the
same residual authority MuJoCo's unconstrained torque simulation does, and
do the best achievable within it rather than chase MuJoCo's ~50%-of-authority
figure on real hardware. Worth stating explicitly in the manuscript as a
limitation/future-work item, not glossed over:

- The 3DOF Hover is a **3-DOF, positive-voltage-only, single fixed-base**
  testbed -- no translational freedom, and Eq. 2.5's `u >= 0` constraint
  (real hardware damage risk if violated) rules out the kind of full-range
  bidirectional residual authority the MuJoCo rotor/torque models allow.
  This is a real, physical constraint, not a software choice.
- **Future work**: the QDrone/QDrone2 platform (6-DOF, full translational +
  rotational freedom -- see the separate virtual-twin track, section 7)
  removes this constraint once its hardware/virtual-twin control channel is
  resolved. Physical Crazyflie (CF2) and Skydio X2-class hardware, matching
  the MuJoCo simulation platforms directly, are a further future-work step
  after that.
- Target for this platform, set 2026-08-27: **>10% mean tracking-error
  improvement over the classical LQR baseline, at matched duration, is a
  legitimate, reportable hardware result** given the constraint above --
  not a shortfall against MuJoCo's number, a different (harder, more
  constrained) regime.

## 5d. Final tuning campaign and recommended configuration

After 5c's finding that β=0.3/max=2V was safe-but-modest and β=0.5/4V then
β=0.4/3V both caused hard45 to overshoot (max error up to 49.7° at
β=0.4/3V, vs. classical's 31.8°), six hypothesis-driven parameter sets
were run across all three dynamic missions (25s, matched to classical),
testing two previously-unvaried dimensions (`--learning-rate`, `--k-error`)
and rate feedback (`--k-rate`, unused all day until here) rather than just
authority (`--beta`, `--max-residual-volts`) alone:

| Set | beta | max-res | lr | k-err | k-rate | hard45 | full3 | yaw360 |
|---|---|---|---|---|---|---|---|---|
| A | 0.15 | 1.0 | 8e-4 | 8 | 0 | +0.60% | +1.86% | +4.99% |
| B | 0.30 | 2.0 | 3e-4 | 8 | 0 | +1.18% | +2.50% | +5.68% |
| C | 0.30 | 2.0 | 8e-4 | 4 | 0 | +0.79% | **-19.87%** (broke, max +12.9deg) | +5.56% |
| D | 0.30 | 2.0 | 3e-4 | 4 | 0 | -0.04% | +2.26% | +4.98% |
| **E** | **0.40** | **3.0** | **3e-4** | **4** | **0** | **+1.23%** | **+2.47%** | **+7.05%** |
| F | 0.30 | 2.0 | 5e-4 | 6 | 2.0 | +0.31% | +2.16% | +3.80% |

**Conclusion: Set E is the recommended final configuration** --
`--beta 0.4 --max-residual-volts 3.0 --learning-rate 0.0003 --k-error 4 --k-rate 0`.
It reuses the *exact* authority level (β=0.4, max_res=3V) that caused the
49.7°-max-error blowup in 5c, but with the learning rate slowed 0.0008 ->
0.0003 and k_error halved 8 -> 4. hard45's max error under Set E is 31.87°
-- essentially identical to classical's 31.835°, confirming the earlier
instability was caused by *how fast the decoder adapted and how quickly
its target saturated*, not by the raw authority level. Set E also produced
the best full3 (+2.47%) and best yaw360 (+7.05%) results of the entire
session.

Two genuinely useful negative findings from this sweep, worth keeping in
mind for any future tuning:
- **Reducing k_error without also slowing the learning rate is dangerous**
  (Set C): full3 regressed -19.87% with a 12.9° max-error jump, the worst
  single result of the day outside the original β=0.4/3V blowup. The two
  parameters interact -- don't change one without the other.
- **Rate feedback (k_rate>0) did not help** (Set F) -- underperformed Set E
  on all three missions despite being specifically designed to target
  hard45's fast, multi-frequency reference. Either the rate estimate
  (`RateFilter`, a 2nd-order filtered derivative) is too noisy/lagged to
  be useful as a learning signal at this k_rate magnitude, or hard45's
  remaining gap isn't a rate-sensitivity problem. Not pursued further this
  session.

hard45 remains the hardest mission to improve -- every tested
configuration clusters around +0.3% to +1.2%, versus full3/yaw360's
2-7% range. This may be a genuine ceiling for this architecture on this
mission (three simultaneously-varying axes, larger amplitude) rather than
a tuning gap; worth flagging as such rather than assuming more sweeping
would close it.

All runs above are n=1 -- see the statistical-robustness item in section 6
before citing these numbers as final.

## 5e. Round 2 tuning (2026-08-28): mission-specific configs beat any global one

After 5d's Set E became the standing recommendation, a fresh Set-E rerun
(with per-neuron `v`/`r` logging now added, see 5f) landed on notably
different numbers than the first Set E run despite identical CLI
arguments -- full3 +2.47% -> +3.09%, yaw360 +7.05% -> **+18.47%** -- a real
signal that the online-PES decoder's learning trajectory has genuine
run-to-run sensitivity, not just measurement noise. Investigating this run
also answered an operator observation: during yaw360, the Back motor (Vb)
sits at 0V for ~98% of the run, in *both* classical and CMG. Root cause,
confirmed from the trace: yaw360 induces a real, sustained ~4 deg pitch
coupling disturbance (physical, not simulated) from the sustained yaw
rotation; `K_LQR`'s pitch-correction terms then push Vb's computed voltage
negative, and the positive-voltage-only law (Eq. 2.5) clips it to 0 rather
than reversing polarity. Not a malfunction -- the controller doing exactly
what it's designed to do.

Given that improved Set E as the new reference, four more configs were run
(one experiment per mission was not the point here -- each set was run on
all three missions, to see how a change tuned for one mission affects the
others):

|---|---|---|---|---|---|---|---|---|---|
| E (reference) | 0.4 | 3.0 | 3e-4 | 4 | 0 | 25 | ~+1% | +3.09% | +18.47% |

**Conclusion: no single global config is best -- mission-specific tuning is

- **yaw360 responds strongly to *every* direction pushed** (more authority,
  lower k-error, or especially more time) -- consistent with it having a
  large, persistent, learnable disturbance (the pitch coupling above) for
  the residual to exploit. **Recommended: Set I** (30s duration) --

- **full3 wants *less* than E, not more** -- every variant this round

- **hard45 has a real, structural ceiling** around +0.3% to +1.2% --
  now confirmed across *ten* distinct configurations spanning both tuning
  rounds, including one that pushed it slightly negative (Set I). This
  reads as a genuine limit given the current authority/shaping envelope,
  not a remaining tuning gap. Going meaningfully past it would mean
  raising authority beyond what's been safety-tested so far -- a real
  trade-off decision, not a parameter default to just change.
