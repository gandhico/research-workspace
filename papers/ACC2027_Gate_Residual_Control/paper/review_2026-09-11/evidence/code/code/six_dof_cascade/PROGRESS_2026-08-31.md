# 6-DOF CMG-PES expansion, 2026-08-31

Extends the CMG-PES residual architecture from 3 channels (attitude torque
only, the existing X2/CF2 MuJoCo work) to 6 channels (position force +
attitude torque), on X2. Two options, per user direction: **B first, kept
lean, as validation before investing in A** (the real payoff, closer to
hardware).

## Option B: fully-actuated 6-DOF wrench (done)

Direct `(Fx,Fy,Fz,tau_x,tau_y,tau_z)` applied via MuJoCo `xfrc_applied`,
bypassing the rotor mixer entirely. Idealized rigid-body testbed (X2
mass/inertia), explicitly **not** a real-quadrotor claim -- built to
observe the 6-channel CMG-PES architecture's own behavior in isolation,
before the underactuation of a real vehicle is added back in (Option A).

- Baseline: position PD + gravity feedforward (world frame) for force,
  existing quaternion PD (body frame, unchanged `kq`/`kw`) for torque.
- CMG-PES: `CMGResidualAugmentor(channels=6, ...)` -- 12 neurons (2 per
  channel), reused unmodified from `gra_control.gate`.
- Torque handled in body frame throughout (matching the existing `omega`
  convention), rotated to world frame only at the final `xfrc_applied`
  write via `R@tau_body`, the same pattern `drone.py` already uses for
  disturbance injection.
- File: `run_6dof_wrench.py`.

### Bug found and fixed before any result was trusted

First smoke test: `hover3d` (should converge to ~0 error) instead averaged
0.90 m position error. Trace inspection showed `z` falling from 1.0 to 0.0
in under a second and sticking there, with `Fz` pinned at a *constant*
value the entire run -- not reacting to error at all. Root cause: the z
force-limit clip (`0.6*mass*gravity`) was applied to the *entire* baseline
force including the gravity feedforward term, which alone needs 100% of
`mass*gravity` just to hover. The clip was cutting the feedforward down to
60% of what's needed before any position correction could even happen --
the drone could never counteract its own weight. Fixed by giving z its own
limit with headroom *above* `mass*gravity` (`1.8*mass*gravity`, x/y
unchanged at `0.6*mass*gravity` since there's no gravity to counteract
laterally). Re-verified: `hover3d` now converges to exactly 0.000 m / 0.000 deg.

### Missions

Four proposed, `position_reference`/`attitude_reference` in `run_6dof_wrench.py`:

| Mission | What it tests |
|---|---|
| `hover3d` | Static 3D point hold -- sanity/regulation floor |
| `waypoint_step` | Discrete jumps between 5 3D waypoints every 9s -- translational analog of `hardstep` |
| `circle_xy` | Smooth circular path, fixed altitude, level attitude -- gentle periodic tracking |
| `full6_stress` | Coupled figure-8-like translation *and* the existing `hard45` attitude profile, simultaneously -- the flagship stress case |

Two more (`figure8_xy`, `helix`) were designed but not run this session --
easy to add later using the same `position_reference` pattern if wanted.

### Reading

Exactly the pattern established across every earlier experiment in this
project (MuJoCo attitude-only missions, the physical Hover campaigns): the
architecture shows **no benefit on gentle/regulation missions** (hover,
simple periodic tracking, discrete steps -- sometimes slightly worse, which
is consistent with PES's own exploration/adaptation adding small overhead
when there's nothing structural to correct) and a **real, large benefit on
the one genuinely demanding mission** that stresses translation and
rotation together at multiple frequencies simultaneously. The attitude
channel's improvement (+49%) is the dominant effect here, similar in
character to the existing hard45 result; the position channel shows a real
but much smaller effect (+4%), plausibly because the position PD baseline
here is comparatively well-tuned relative to what it needs to correct
within this idealized fully-actuated setup.

This validates the 6-channel CMG-PES mechanism works correctly (after the
force-limit bug fix) and behaves consistently with everything already
known about the architecture. Per direction, not pursuing more tuning here
-- moving to Option A.

## Option A: realistic underactuated cascade (next, not started)

The actual payoff -- closer to real hardware, per user's explicit
interest ("closest to hardware, as we did with Nengo"). Design:

1. Outer position loop: same `F_0 = mass*g*z_hat - Kp(p-p_ref) - Kd(v-v_ref)`
   as B, but decomposed into desired collective thrust (`||F_0||`) and a
   desired body attitude (tilt so the thrust axis points along `F_0`) --
   standard differential-flatness quadrotor control, not a new invention.
2. Inner attitude loop: existing quaternion-PD tracks that *commanded*
   attitude (not a fixed external reference) plus the mission's own yaw.
3. CMG-PES: still 6 channels, but now correcting two cascaded things -- a
   3-channel position-residual (adjusting the desired-tilt/thrust command)
   and the existing 3-channel attitude-residual (adjusting body torque) --
   not a flat 6-DOF wrench.
4. Actuation goes back through the real rotor mixer (`_mixer`, `B_inv`
   from `drone.py`) -- the actual underactuated X2 model, not direct
   `xfrc_applied`. This is the part that makes it "closer to hardware":
   real 4-actuator authority, real saturation, no assumption of
   independent lateral force.

Known hard part: thrust-vector-to-attitude conversion has a singularity
when the desired force points straight down (thrust axis inverted) --
needs explicit handling, not just a naive `atan2`.

### Debugging journey: a persistent instability, and its real root cause

First implementation (`run_6dof_cascade.py`) built as designed above:
position PD -> `thrust_vector_to_attitude` (Mellinger-Kumar decomposition,
`rotmat_to_quat` via Shepperd's method) -> existing quaternion-PD inner
loop -> real rotor mixer. First smoke test (`hover3d`, should hold exact
equilibrium): held exact zero error for >10s, then diverged exponentially
from floating-point-noise level with no external trigger. Classic
right-half-plane-pole signature, not a disturbance.

Three empirical mitigations were tried, each attacking a plausible cause,
each reducing but not eliminating the divergence -- itself informative,
since "delays onset without eliminating it" is the signature of nudging
system parameters without actually crossing an unstable eigenvalue's real
part through zero:

1. **Slowed the position loop** (`wn_pos` 3 rad/s -> 1.0-1.2 rad/s) for
   proper cascade time-scale separation from the attitude loop (4 rad/s).
   Delayed onset (~10.5s -> ~16.7s), did not eliminate.
2. **Low-pass filtered the commanded attitude** `q_des` (alpha=0.02).
   Further reduced growth rate, still diverged.
3. **Added angular-rate feedforward** to the inner loop: rather than
   driving `omega` to zero (correct only when the attitude reference is
   external and static, as in every earlier mission in this project),
   estimate `omega_des` from how fast `q_des` itself is rotating (finite
   difference of the commanded attitude) and drive `omega - omega_des` to
   zero instead. Stable to 25s, still diverged by 45s (pos_err=6.42m,
   qerr=3.46deg) -- same signature, just delayed further.

Per user direction ("take your time... report everything, is
interesting"), rather than keep patching empirically, did a **linearized
eigenvalue analysis** (`linearize_cascade.py`): reduced the coupled
y-position/roll subsystem to 4 states `[y, vy, phi, omega_x]`, built the
closed-loop dynamics by reusing the actual `thrust_vector_to_attitude` and
`quat_error` functions (not hand-derived approximations of them), and
took a numerical Jacobian at the hover equilibrium. Found a genuine
eigenvalue with positive real part (+2.66 without feedforward, +2.92
with) in both variants -- independent confirmation that this is a real
instability, not a numerical artifact of one particular sim run.

Interpreting *why* that eigenvalue was positive led to an apparent
contradiction: manually evaluating `quat_error` for a positive-roll
perturbation against a fixed identity reference gave a torque that looked
like it was pushing the *wrong* way -- yet the identical formula
(`-kq*eq-kw*omega`) is the same one validated stable for months across
every earlier attitude-only mission in this project (`drone.py`, hard45,
etc). That contradiction was the real clue, not a red herring to
explain away.

Per user guidance ("adopt a reference facade formula" if the historical
TriRotor reference wasn't reachable -- it wasn't, D: drive was
disconnected at the time), and per the user's explicit follow-up
("continue using the quaternions model we did... our baseline is
quaternions, here and forward") -- rather than switch formalism (e.g. to
a rotation-matrix/SE(3) geometric controller), the investigation stayed
in quaternions and instead **verified everything against real MuJoCo
ground truth, empirically, one link at a time**, rather than trusting
more hand-derivation (which had already produced one contradiction):

1. Applied a small constant `tau_x` through the *real* mixer, from rest,
   and read `omega_x` back from `data.qvel` directly. Positive torque ->
   positive `omega_x`, growing smoothly. No sign flip in the mixer or
   Euler's-equation direction.
2. Extended that same test over a longer window and additionally read the
   *actual* roll angle back out (via `quat_error` against identity,
   through the same `quat_conj(data.qpos)` conversion the controller
   itself uses for `q_meas`). Found `omega_x` positive while the
   recovered roll angle grew *negative* -- an apparent sign mismatch
   between `omega` and the attitude representation. This turned out to be
   a distraction (see below): it was a symptom of the *representation*
   difference, not the rate itself, and is not the bug.
3. **The decisive test**: set the plant to a real, small tilt directly via
   MuJoCo `qpos` (ground truth, no formulas), read the plant's *actual*
   physical thrust direction via `data.xmat` (also ground truth), fed that
   *exact* direction into `thrust_vector_to_attitude`, and compared the
   resulting `q_des` against `q_meas` (built the same way the controller
   itself builds it, `quat_conj(data.qpos)`). For a plant already at the
   exact attitude that produces a given thrust direction, `q_des` for that
   same direction should reproduce `q_meas` almost exactly. Instead, across
   three tested angles (0.05, -0.05, 0.15 rad), `q_des` reproduced
   `quat_conj(q_meas)` -- the *opposite* convention -- exactly.

**Root cause**: `q_meas` is built as `quat_conj(data.qpos[...])` to convert
MuJoCo's raw attitude quaternion into this codebase's own quaternion
convention -- a conversion this project has needed since the very first
attitude-only missions. `q_des`, computed fresh each step from a geometric
rotation matrix (`rotmat_to_quat(R_des)`, built from textbook world-frame
basis vectors) never went through that same conversion. `quat_error(q_des,
q_meas)` was therefore comparing two quaternions in opposite conventions
the entire time -- not randomly wrong, but consistently computing
*roughly twice the true angular error*, with a sign that turns what should
be a restoring torque into a driving one. That is exactly the
runaway-from-floating-point-noise signature observed in every single
empirical test, and exactly the kind of closed-loop pole a linearization
around that same (buggy) formula would find. It also explains why the
identical `-kq*eq-kw*omega` formula was never at fault: it is correct;
what was wrong was the convention of one of its two inputs, introduced
only in Option A because Option A is the first place in this project that
computes an attitude reference from geometry rather than from
`euler_to_quat` directly.

**Fix**: one line, `q_des = quat_conj(q_des)` immediately after
`thrust_vector_to_attitude`, before `q_des` is used anywhere (inner-loop
error, rate feedforward, or logging). Verified: `hover3d` at 45s now
converges to exactly 0.0000 m / 0.000 deg, identical to Option B's
already-validated hover3d result.

With the real bug fixed, re-checked whether the three earlier mitigations
were actually necessary or were compensating for the same underlying bug.
Tried reverting the position-loop slowdown (`wn_pos` back up to
[2.5,2.5,3.0], then an intermediate [1.8,1.8,2.0]): both destabilized
*even the now-fixed hover3d* case. So the cascade time-scale-separation
requirement was real and independent of the convention bug -- both
problems existed simultaneously, and the original mitigation #1 was a
correct, necessary design choice, not a workaround for the real bug.
Kept `wn_pos=[1.0,1.0,1.2]` (documented reasoning already in the code).

### Reading

A cleaner, more coherent result than Option B, and arguably more
meaningful because it comes from the *realistic* underactuated system: on
`hover3d` (no structural error to correct) CMG-PES adds a small amount of
its own exploration noise and no benefit, consistent with every earlier
experiment in this project. On every mission with real, sustained tracking
demand, CMG-PES helps, and the size of the benefit scales with how hard
the classical baseline's bandwidth-limited cascade struggles:
`waypoint_step` (discrete jumps the ~1 rad/s position loop can mostly
keep up with between jumps) sees a modest +11-13%; `circle_xy` and
`full6_stress` (continuous, faster-than-position-bandwidth demand) see
the real cascade's classical baseline struggling hard (0.88-0.99 m mean
error, 14-15 deg attitude error) and CMG-PES recovering 65-76% of that
error. This is a materially larger and more consistent effect than
Option B's idealized wrench showed on the same style of missions (+4% to
+49%), which makes sense: the realistic cascade's classical baseline has a
harder job (bandwidth-limited by construction, real actuator mixing, no
independent lateral force), giving the adaptive architecture more genuine
structural error to correct against -- exactly the "closer to hardware"
regime the user asked to prioritize.

Per user direction, extended Option A across both platforms in this
project's scope (`x2`, `cf2-rotor` -- 3DOF Hover explicitly deferred to
the future QDrone2 work, not touched here), implemented the same
architecture natively in Nengo, and validated it against LIF, ALIF,

### CF2 platform (`cf2-rotor`: real rotor mixer, not the virtual-wrench `cf2` spec)

`run_6dof_cascade.py` generalized to accept `--platform`; `torque_limits`
already took a platform name, `_mixer`/`SPECS` were already
platform-agnostic. Since every gain formula in the cascade is written in
terms of natural frequency (`kp=mass*wn^2`, `kq=2*inertia*wn^2`, etc.),
force/torque limits as mass/inertia fractions, the *classical* baseline
transferred to CF2 (~50x lighter, ~1000x smaller inertia than X2) with
**zero retuning** -- hover3d converges exactly, and the other three
missions land within a few percent of X2's classical numbers. That
dimensional-scaling design paid off directly.

CMG-PES did not transfer as cleanly. At X2's tuning (beta=0.5,
lr=8e-4) CF2 diverged badly, including at hover3d (which is trivial for
every other configuration tested this project) -- inspecting the trace
showed the z-height oscillating wildly (1.0 -> 0.10 -> 0.98 -> 0.09 ->
1.34m) before crashing. Swept beta down (0.5 -> 0.15 -> 0.1 -> 0.05 ->
0.02 -> 0.01) and learning_rate down (8e-4 -> 2e-4): hover3d stabilizes
by beta~0.05, but the three tracking missions only ever *approach*
classical's error asymptotically as beta shrinks toward zero -- never
beat it. That asymptotic-without-crossing pattern (unlike Option A's
earlier instability, which had a clear before/after fix) means this is a
real, reportable finding rather than a residual tuning gap: **this
particular CMG-PES configuration provides no net benefit on CF2**, even
after the retuning needed just to stop it from crashing. Locked in
beta=0.02, lr=2e-4 (real gain at hover, least-bad on the rest) for the
final comparison.

### Neuron-family validation on the 6-channel cascade

`nengo_neuron_family_6dof.py` generalizes the existing 3-channel
`NengoNeuronFamilyAugmentor` (frozen, backs the published
`NENGO_NEURON_FAMILY_BENCHMARK_2026-08-31.md`, not touched) to an
arbitrary channel count, reusing its exact paired-current /
low-pass-feature / PES-decoder pattern and the same per-family
calibration (`feature_calibration.json`: feature_scale, native_current_scale
for `lif`, `alif`, `izhikevich`, `lifrate`).

First attempt at CMG's own tuning (beta=0.5, lr=8e-4) diverged violently
for every spiking family, including at hover3d -- trace inspection showed
`residual_norm` slamming to ~11.7 (near the theoretical max for beta=0.5)
within 0.15s, while `pos_err` was still 0.009m: the low-pass spike-trace
feature hadn't settled yet and its transient/noisy value was being
decoded, clipped to +-1, and applied at close to full residual authority
almost immediately. Swept beta/lr down aggressively (to 0.01/1e-4, ~50x
below CMG's own setting) -- at that point every family is well-behaved at
hover3d, but under `full6_stress` (the demanding, coupled mission), LIF,
ALIF, and Izhikevich **still diverge** (22-25 deg mean attitude error,
worse than classical's 14.6deg) even at this heavily reduced authority.

The cleanest evidence came from also testing **LIFRate** -- same tuning
curve family as LIF, but a deterministic rate model with no spike
discretization. LIFRate stayed near classical's baseline on both missions
(0.89m/14.1deg on full6_stress vs classical's 0.99m/14.6deg -- roughly
neutral, not diverging). That isolates the destabilizing factor
specifically as **spiking discretization noise**, not the neuron model's
tuning curve or its being a "conventional" (non-CMG) unit per se: CMG's
smooth, continuous, noise-free membrane/gate output can carry a well-formed
residual through fast, tightly-coupled 6-DOF dynamics at strong authority
(beta=0.5) that no spiking alternative survived even at 1/50th that
authority.

## CF2 revisited: was the classical baseline actually well-tuned?

Per user direction: before trusting CF2's negative result, get a properly
tuned classical (PID) baseline first, independently for CF2, rather than
reusing X2's gains just because they were dimensionally stable there too.
That distinction matters -- "doesn't diverge" and "is well-tuned" are not
the same claim, and the original CF2 numbers only established the former.

### Attitude-loop bandwidth was badly under-tuned

Swept `wn_att` on `full6_stress` (fixing `wn_pos=[1,1,1.2]`, X2's value):
CF2 stayed *stable* at hover3d all the way out to `wn_att=25` (vs. X2's
practical ceiling around 4), confirming the earlier suspicion that gains
copied from X2 were nowhere near CF2's actual limit. On the demanding
mission itself, tracking accuracy kept improving well past X2's wn_att=4:

| wn_att (x,y,z) | full6_stress pos err (m) | att err (deg) |
|---|---:|---:|
| [4, 4, 3.5] (X2's value, unchanged) | 0.7849 | 14.001 |
| [8, 8, 7] | 0.2895 | 0.518 |
| [12, 12, 10] | 0.2851 | 0.302 |
| [16, 16, 13] | 0.2825 | 0.213 |
| [20, 20, 17] | 0.2809 | 0.164 |

Diminishing returns past ~12-16, so no need to push to the stability edge.

### Position-loop bandwidth: a real ceiling, and a real tradeoff

With the attitude loop faster, cascade separation allows a faster position
loop too. Swept `wn_pos` at `wn_att=[16,16,13]`: full6_stress kept
improving through `wn_pos=[3,3,3.6]` (0.109m/1.20deg) then collapsed at
`[4,4,4.8]` (2.89m/124.6deg) -- the same kind of cascade-separation
boundary found earlier, now located for CF2 specifically rather than
assumed from X2.

But pushing bandwidth that hard revealed a genuine tradeoff the smooth
missions don't show: `waypoint_step` (discrete jumps) got *worse* at high
bandwidth (0.174m/9.85deg at wn_pos=[3,3,3.6] vs. 0.159m/2.89deg at the
original untuned gains) -- large instantaneous errors at each jump drive
`kp_pos*(error)` straight into force saturation at high kp, producing a
bang-bang-like overshoot/ringing response that a slower loop doesn't
trigger. Backed off to a balanced compromise, `wn_pos=[2,2,2.4]`,
`wn_att=[12,12,10]`, which improves every mission simultaneously
(including waypoint_step, which *also* got better here, not just the
smooth-reference ones):

| Mission | untuned classical | well-tuned classical | improvement |
|---|---:|---:|---:|
| hover3d | 0.0000m / 0.000deg | 0.0000m / 0.000deg | already exact |
| waypoint_step | 0.1591m / 2.893deg | 0.0401m / 1.813deg | **-75% pos** |
| circle_xy | 0.7539m / 12.980deg | 0.2248m / 0.495deg | **-70% pos, -96% att** |
| full6_stress | 0.7849m / 14.001deg | 0.1587m / 0.549deg | **-80% pos, -96% att** |

### Was it actually missing an I-term? Tested, not assumed

The user asked for a "PID" baseline specifically, so integral action was
implemented (not just assumed unnecessary): anti-windup-clamped position
and attitude integrators added to `run_6dof_cascade.py` (`--ki-pos`,
`--ki-att`, both default 0, X2 unaffected -- verified exact regression
match on X2 full6_stress after the change). Tested `ki_pos` at a standard
PID-zero-placement heuristic (`ki ~ 0.3*kp*wn`) and at 10x smaller: both
made every mission slightly *worse*, not better (e.g. full6_stress
0.159m/0.55deg with PD-only vs. 0.190m/0.71deg at the heuristic ki). This
makes sense in hindsight -- every mission here is a *tracking* problem
against a moving reference, not *regulation* against a static bias or
disturbance, which is where integral action earns its keep. Conclusion:
**ki=0 is the genuinely well-tuned choice for these missions**, arrived at
by testing, not by omission.

### CMG-PES against the properly-tuned baseline

Re-ran CMG-PES on top of the well-tuned baseline. beta=0.5 (still X2's
setting) was still unstable, confirming CF2's residual-authority ceiling

### Reading

The deeper investigation changes the story in an important way, but
doesn't reverse it. CF2's original "negative result" was partly an
artifact of an under-tuned classical baseline -- once genuinely tuned
(attitude bandwidth was the dominant lever; position bandwidth and an
explicitly-tested integral term contributed less), CF2's classical
controller alone gets *dramatically* better (full6_stress: 14.0deg ->
0.55deg attitude error, an 96% reduction, with no learning architecture
involved at all). Against that much stronger baseline, CMG-PES no longer
looks actively harmful (as it did against the weak baseline) -- it gives
a small, consistent position improvement (+3-5% on the demanding
missions) at a small attitude cost (-18-23%), a genuine mixed trade-off
rather than a clear win or a clear loss.

## More powerful CF2 rotors: tested, doesn't change the picture

User's follow-up question referenced two remembered figures from earlier,
unrelated work -- worth clarifying since they don't both belong to the
same study: the ~60% figure is real and comes from an earlier attitude-only
(3-channel) campaign in this project using `cf2-rotor` at
`--actuator-scale=1.5` (`PROJECT_STATUS_TABLE_2026-08-31.md`, yaw360:
60.60%); the ~86% figure is real too but from a *different, older* project
(`P3_Gate_Residual/learned`), comparing learning *mechanisms* (a learned
gate decoder) on the *stock* (1x, unscaled) Crazyflie -- not a rotor-power
design variant at all. There is no existing "Nx design" in this repo that
produced 86%.

Given that, tested the actual proposal directly: does a more-powerful-rotor
CF2 redesign change the 6-DOF cascade picture? Added `--actuator-scale`
(motor thrust ceiling, same mechanism as `drone.py`'s existing flag) and a
new `--authority-scale` (the *design* force/torque ceiling the controller
is allowed to request -- `force_limits`/`tau_limits`, which don't move with
`actuator_scale` alone) to `run_6dof_cascade.py`. X2 unaffected at defaults
(regression-checked, exact match).

- **At the well-tuned baseline** (`wn_pos=[2,2,2.4]`, `wn_att=[12,12,10]`),
  1.5x actuator_scale changes *nothing* (identical to 4 decimal places) --
  motors were never the binding constraint there.
- **At the more aggressive tuning** that was backed away from earlier
  (`wn_pos=[3,3,3.6]`, `wn_att=[16,16,13]`, which won on full6_stress/
  circle_xy but lost badly on waypoint_step's step overshoot): 1.5x actuator
  power *did* help the aggressive tuning's worst case (full6_stress at
  `wn_pos=[3.5,3.5,4.2]`, previously unstable, improved from 1.58m/66deg to
  0.94m/24.7deg) -- but 1.5x and 3.0x gave *identical* results, and neither
  beat the already-known best tuning at 1x power (`wn_pos=[3,3,3.6]`,
  0.109m/1.20deg). So extra power partially compensates for a badly-chosen
  gain, but never exceeds a well-chosen one.
- **waypoint_step's overshoot did not improve with more power** -- still
  0.174m/9.87deg at 1.5x actuator_scale, same as 1x. Raising
  `authority_scale` alongside it made this *worse* (0.188m/12.25deg): the
  original, lower force ceiling was accidentally acting as anti-windup
  during the step transient, and removing that ceiling let the controller
  swing harder into the same overshoot, not less.
- **CMG-PES with more authority** (1.5x actuator+authority at the balanced
  tuning): essentially unchanged from the 1x-authority result (0.150m/0.69deg
  vs. 0.151m/0.65deg) -- the extra residual headroom exists but isn't being
  used, because CMG-PES's typical output wasn't saturating near the old
  ceiling in the first place.

**Conclusion**: CF2's behavior in this cascade is not actuator-power-limited
at any point tested. The two real ceilings found -- cascade time-scale
separation (a closed-loop stability boundary) and step-response overshoot
(a proportional-gain/reference-shaping issue) -- are both control-theoretic,
not hardware. A "more powerful CF2" redesign is a reasonable hypothesis but
does not reproduce anything like X2's dynamics or unlock a bigger CMG-PES
benefit here, because the thing that makes CF2 different from X2 was never
motor power -- it's the ~50x lower mass and ~1000x lower inertia, which
is a property of the airframe, not the rotors.

The honest conclusion: **CF2 does not replicate X2's large win, even
against its best available classical baseline** -- but the *reason* is now
far more defensible than before. X2's classical baseline has real,
substantial structural error for CMG-PES to correct (full6_stress:
0.99m/14.6deg even at X2's own well-established tuning); CF2's classical
baseline, once properly tuned, is already extremely accurate (0.16m/
0.55deg) precisely because CF2's tiny inertia lets its attitude loop run
far faster than X2's actuators allow. There is very little structural
error left on the table by the time CMG-PES gets involved, and what
residual authority is left mostly trades a little position accuracy for a
little attitude noise. This is consistent with, and sharpens, the
platform-dependent story that was already emerging: **CMG-PES's benefit
tracks how hard the classical baseline is actually struggling**, and a
platform whose physical scale grants an unusually fast, easy-to-control
inner loop leaves correspondingly less for the architecture to add --
which is itself a legitimate, useful, and testable characterization of
where this architecture pays off, not a weakness in the result.
